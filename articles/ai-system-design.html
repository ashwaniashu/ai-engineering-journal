SYSTEM DESIGN

GenAI System Design: Latency, Caching and Reliability

A practical guide to designing production GenAI APIs that are measurable, resilient, cost-aware, and safe under partial failure.

By Kumar Ashwani · AI Engineering Journal · Practical engineering guide

Start with the request path

A production GenAI request may pass through an API gateway, authentication, input validation, retrieval, one or more model calls, post-processing, and response streaming. Before optimizing, measure each stage independently. A user-visible response time of ten seconds does not prove the model call itself takes ten seconds.

Measure latency by stage

Record timestamps around authentication, retrieval, reranking, prompt construction, model time-to-first-token, generation, and serialization. Use traces with a shared request ID so one slow request can be followed across services. Track p50, p95, and p99 latency rather than only averages.

Use timeouts and bounded retries

Set a deadline for the entire request and smaller timeouts for downstream calls. Retry only transient failures, cap attempts, add exponential backoff with jitter, and avoid retrying after the overall deadline. Retrying every failure can multiply load during an outage.

Cache carefully

  • Exact-response cache: reuse results for identical, safe requests.
  • Semantic cache: reuse an answer for a meaningfully similar query only when similarity and correctness thresholds are appropriate.
  • Retrieval cache: reuse retrieved candidates when the query and underlying content version permit it.

Cache keys must include relevant tenant, permission, model, prompt, and data-version context. Never allow a cached answer or retrieved document from one user to leak to another. Define expiration and invalidation rules when source content changes.

Control model cost and throughput

Track input and output tokens, model selection, retries, and cost per successful task. Limit prompt size, retrieve only useful context, choose a model that meets the quality target, and use asynchronous work for tasks that do not need an immediate response. Apply rate limits and concurrency limits to protect downstream services.

Design for partial failure

Define what the system should do if retrieval is unavailable, a model provider times out, or a tool returns invalid data. Depending on the use case, return a clear temporary error, offer a limited fallback, or queue work for later. Do not silently fabricate an answer when required evidence is missing.

Observability checklist

  • Request ID and stage-level latency
  • Model and prompt version
  • Token usage and estimated cost
  • Retrieval result IDs and evaluation signals
  • Timeouts, retries, rate-limit events, and tool errors
  • Quality feedback and representative offline evaluation results

Protect observability data: redact secrets, minimize sensitive user content, restrict access, and set retention policies. Logs should help diagnose the system without becoming a second source of sensitive data.

Engineering takeaway: production GenAI requires ordinary distributed-systems discipline plus model-specific quality and cost monitoring. Measure first, then optimize the bottleneck you can prove.
